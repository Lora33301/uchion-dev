  ---
  Вердикт: выдержит ли 500-1000 пользователей?

  500 одновременных пользователей — да, с оговорками. 1000 одновременных генераций — нет без доработок.

  Главные узкие места не в размере файлов, а в runtime-архитектуре:

  1. Puppeteer — новый браузер на каждый PDF (КРИТИЧНО)

  browser = await puppeteer.launch(...)  // каждый раз новый Chromium
  Каждая генерация поднимает отдельный процесс Chromium (100-300 MB RAM). 10 одновременных генераций = 1-3 GB RAM только на PDF. Это главный bottleneck.

  Решение: Browser pool (один Chromium, переиспользуемые страницы) — уменьшит потребление в 5-10 раз.

  2. Нет очереди задач — генерация синхронная

  Полный цикл генерации (AI → валидация → агенты → фикс → PDF) занимает 30-120 секунд и держит HTTP-соединение открытым всё это время. Нет job queue — все запросы обрабатываются параллельно без ограничений.

  Решение: BullMQ или аналог — ограничить concurrency до 3-5 генераций.

  3. pdfBase64 хранится в БД как текст

  Каждый worksheet хранит PDF (200-500 KB base64) в JSON-колонке. При запросе списка рабочих листов все эти blob'ы тянутся из БД.

  Решение: S3/файловая система для PDF, в БД только URL.

  4. DB pool = 10 соединений

  Для текущей нагрузки хватает. При 50+ одновременных запросах (генерация + API + webhooks) — будет bottleneck.

  5. Нет compression middleware

  Большие base64-ответы идут без сжатия. На слабом интернете — ощутимо.

  ---
  Что хорошо в архитектуре

  - shared/ — единый источник типов и схем, без дублирования frontend/backend
  - Config-driven generation — новые предметы через конфиги, не код
  - Redis-first rate limiting с in-memory fallback — правильный паттерн
  - Refresh token rotation с familyId — корректная защита от кражи токенов
  - Атомарный декремент генераций — race condition невозможен
  - Middleware-цепочка — CORS, CSRF, security headers — всё на месте
